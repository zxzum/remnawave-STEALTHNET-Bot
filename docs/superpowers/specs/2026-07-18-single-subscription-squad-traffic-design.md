# Обычная Remnawave-подписка и локальный учет трафика squad — Design

**Дата:** 2026-07-18  
**Целевая ветка:** текущее состояние `main`; локальная `feature/composite-subscriptions` уже полностью входит в историю `main` и отстает от него  
**Статус:** согласовано в диалоге, ожидает финального просмотра перед выпуском четырех планов-ТЗ

## 1. Цель

Сохранить все полезные доработки проекта, полностью удалить архитектуру composite subscription и вернуть каждому клиенту одну обычную подписку Remnawave с одним Remnawave user и одной рабочей subscription URL.

Поверх обычной подписки STEALTHNET должен уметь учитывать локальный лимит трафика только для одного выбранного squad тарифа. Для тарифа со squad `Default` и `Whitelist` администратор выбирает `Whitelist` как учитываемый squad; трафик нод `Default`/EU не списывается.

## 2. Зафиксированные продуктовые правила

### 2.1 Одна подписка

- Одна запись STEALTHNET `Subscription` соответствует одному Remnawave user.
- У подписки один `remnawaveUuid`, одна обычная Remnawave subscription и одна стабильная публичная ссылка STEALTHNET.
- `RemnawaveComponent`, tariff/trial component overrides, объединение нескольких upstream subscription и создание дополнительных Remnawave users удаляются полностью.
- Подарки, trial, дополнительные логические подписки, промокоды, автопродление, HWID, публичная страница, конвертация и другие независимые функции сохраняются.

### 2.2 Режим лимита тарифа

В тарифе выбирается список доступных squad, например:

```text
Default
Whitelist
```

После этого администратор выбирает один взаимоисключающий режим:

1. `REMNAWAVE` — используется обычный глобальный лимит и reset strategy Remnawave; локальная тарификация недоступна.
2. `LOCAL_SQUAD` — из уже выбранных squad выбирается ровно один учитываемый squad, например `Whitelist`; Remnawave user получает глобальный лимит `0` и `NO_RESET`, а лимит и персональные периоды ведет STEALTHNET.

Для `LOCAL_SQUAD` форма содержит только:

```text
Учитываемый squad: Whitelist
Лимит: N ГБ
Сброс: ежемесячно от даты начала периода
```

Ручной выбор pool, hidden hosts и Node UUID отсутствует.

### 2.3 Trial

- Trial имеет собственную конфигурацию лимита, независимую от тарифа.
- Trial поддерживает те же режимы `REMNAWAVE` и `LOCAL_SQUAD`.
- Для локального режима Trial выбирает учитываемый squad только из назначенных ему squad.
- Конвертация Trial в платный тариф завершает trial-период и создает период правил выбранного тарифа без переноса trial-трафика.

### 2.4 Персональные дополнительные гигабайты

Используется одна модель начислений с двумя типами:

- `CURRENT_PERIOD` — увеличивает лимит только текущего периода и сгорает при его завершении; этот тип будет использовать будущая покупка пакета гигабайт.
- `WHILE_TARIFF_ACTIVE` — прибавляется в каждом новом периоде, пока активен тот же тариф.

При продлении того же тарифа `WHILE_TARIFF_ACTIVE` сохраняется. При переходе вверх или вниз на другой тариф начисление удаляется и при последующем возврате не восстанавливается.

### 2.5 Персональный месячный период

- Первый период начинается в момент успешной покупки/активации.
- Следующий период начинается в ту же календарную дату и время следующего месяца.
- Для даты, которой нет в следующем месяце, используется последний день месяца.
- Продление той же активной подписки не сдвигает текущую границу периода и не обнуляет трафик досрочно.
- Когда подписка остается оплаченной после `periodEndsAt`, создается следующий период и лимит сбрасывается.
- Если подписка закончилась, новый период не открывается до успешного продления.

## 3. Автоматический выбор учитываемых нод

Администратор выбирает только squad тарифа и указывает, какой из них учитывается локально:

```text
Назначенные squad: Default + Whitelist
Учет трафика: Whitelist
```

STEALTHNET запрашивает `GET /api/internal-squads/{uuid}/accessible-nodes` и автоматически получает актуальные Remnawave Node UUID выбранного `Whitelist` squad. Bulk-статистика запрашивается только для этих нод. Ноды `Default`/EU в запрос не включаются и их трафик не списывается.

Состав нод обновляется при сохранении тарифа, при запуске backend и периодически в фоне. Изменение hidden hosts, Xray/Mihomo balancer или его тегов не требует изменения тарифа STEALTHNET.

Приложенная конфигурация использует:

```text
auto-wl               -> selector eu -> обычный EU-трафик, не учитывать
whitelist-balancer    -> selector wl -> учитывать
```

Эта структура остается деталью Remnawave. В админке STEALTHNET не появляются поля `auto-wl`, `whitelist-balancer`, host UUID или Node UUID. Найденные ноды можно показать только как read-only диагностику.

Если Remnawave не возвращает ноды выбранного squad, учет получает состояние `CONFIG_ERROR`, enforcement приостанавливается, пользователь сохраняет доступ, а администратор получает предупреждение.

## 4. API-брокер статистики

### 4.1 Источник

Минимальная поддерживаемая версия Remnawave — `2.8.0`. Основной источник — официальный пакетный endpoint:

```http
POST /api/bandwidth-stats/nodes/users?start=YYYY-MM-DD&end=YYYY-MM-DD&topUsersLimit=N
Content-Type: application/json

{"nodesUuids":["..."]}
```

Endpoint возвращает суммарные байты выбранных нод по `username`. В STEALTHNET у обычной подписки сохраняются `remnawaveUuid`, `remnawaveUsername` и `remnawaveShortUuid`, поэтому сопоставление выполняется локально без запроса на каждого пользователя.

`topUsersLimit` устанавливается выше числа локально учитываемых пользователей. Если ответ содержит ровно лимит строк, выборка считается потенциально обрезанной: данные не применяются, доступ не отзывается, создается диагностическое событие.

Прямой read-only доступ к PostgreSQL Remnawave не является основной архитектурой. Он допускается как изолированный fallback adapter только если обязательный spike на установленной версии докажет, что официальный endpoint не возвращает полную выборку или не выдерживает целевую нагрузку.

### 4.2 Ограниченный checkpoint

На подписку существует не более одной строки checkpoint:

```text
subscriptionId (unique)
squadUuid
currentDate
currentObservedBytes
previousDate
previousObservedBytes
updatedAt
```

Новая запись на каждый пятиминутный опрос не создается. Текущий и предыдущий день занимают два переиспользуемых слота одной строки. Предыдущий день повторно проверяется для учета запоздавшей статистики Remnawave.

Запись выполняется только если значение изменилось. Все изменения одного прохода применяются пакетно в одной транзакции. История каждого sample не хранится; аудит создается только для значимых бизнес-событий.

### 4.3 Расчет

```text
delta = currentObservedBytes - savedObservedBytes
```

- Положительный `delta` прибавляется к активному локальному периоду.
- Повторный ответ с тем же значением ничего не начисляет.
- Уменьшившийся источник не уменьшает уже учтенный трафик; checkpoint обновляется и создается anomaly event.
- Старые whitelist-счетчики при миграции не переносятся. В момент cutover создается baseline, поэтому исторический трафик не начисляется.

### 4.4 Расписание и отказоустойчивость

- Обычный проход: раз в 5 минут.
- Для остатка не более 10%: раз в минуту.
- Открытие новых персональных периодов: раз в минуту.
- В нескольких экземплярах backend воркер защищается PostgreSQL advisory lock/эквивалентной существующей leader-защитой.
- При недоступности или неполном ответе Remnawave действует fail-open: данные не изменяются, squad не отзывается, попытка повторяется.
- Предельный перерасход ограничен трафиком за интервал между измерениями.

## 5. Лимит, уведомления и enforcement

Эффективный лимит периода:

```text
base tariff/trial limit
+ active WHILE_TARIFF_ACTIVE grants
+ CURRENT_PERIOD grants
```

Один раз за период отправляются уведомления при остатке не более `50%`, `25%`, `10%`, `3%` и `0%`. Если один sample пересек несколько порогов, отправляются все пропущенные уведомления в порядке убывания остатка. Уведомление `0%` содержит `periodEndsAt`.

При исчерпании:

1. Локальный период идемпотентно получает статус `EXHAUSTED`.
2. У пользователя через Remnawave API удаляется только учитываемый `Whitelist` squad.
3. `Default` и остальные squad, expireAt, HWID и обычная subscription остаются действующими.
4. При новом периоде, `CURRENT_PERIOD` top-up или административном восстановлении `Whitelist` возвращается, если доступный лимит снова больше использованного.

Полный `revoke` подписки остается отдельным административным действием и отзывает обычную Remnawave subscription целиком.

## 6. Конвертация тарифа

- Существующая формула пересчета стоимости остатка в дни нового тарифа сохраняется для перехода вверх и вниз.
- Конвертация выполняется над той же одной `Subscription` и тем же одним Remnawave user; component users не создаются.
- Срок, рассчитанный формулой, записывается одинаково в STEALTHNET и `expireAt` Remnawave.
- При смене тарифа завершается старый локальный период, удаляются `WHILE_TARIFF_ACTIVE` старого тарифа и создается новый период с лимитом нового тарифа.
- Переход между `REMNAWAVE` и `LOCAL_SQUAD` атомарно меняет глобальный лимит Remnawave, reset strategy, squad membership и локальное состояние.

## 7. Полная интеграция с админ-панелью

### Тарифы и Trial

- Создание, редактирование, копирование и просмотр тарифа показывают режим лимита.
- При `LOCAL_SQUAD` учитываемый squad выбирается только из уже выбранных squad.
- При `REMNAWAVE` локальные поля скрыты/заблокированы; при `LOCAL_SQUAD` недоступны поля глобального Remnawave-лимита.
- Отдельная конфигурация Trial использует те же проверки.

### Клиент и подписка

Карточка одной обычной подписки показывает:

- тариф, статус и expireAt;
- используемый локально squad;
- использовано, лимит, остаток и процент;
- начало и конец персонального периода;
- дополнительные гигабайты по типам;
- отправленные пороги и краткий аудит;
- здоровье последней синхронизации.

Действия администратора:

- выдать `+N ГБ` на текущий период;
- выдать `+N ГБ` на время текущего тарифа;
- отозвать конкретное начисление;
- пересчитать/синхронизировать одного клиента;
- временно приостановить или восстановить локальный доступ;
- полностью revoke обычной подписки.

### Диагностика

- Последний успешный проход, длительность, число обработанных пользователей.
- Возраст данных, ошибки Remnawave, обрезанная выборка, конфигурационные ошибки squad.
- Число активных/исчерпанных периодов и максимальный зарегистрированный overshoot.
- Автоматически найденные ноды выбранного squad только для чтения.

## 8. Миграция текущих клиентов

### 8.1 Подготовка

До удаления composite-кода создается snapshot каждого клиента:

- STEALTHNET subscription, tariff/trial и владелец;
- исходный `createdAt` и точный `expireAt`;
- статус, HWID, обычные squad;
- все component UUID, username, short UUID и публичные ссылки;
- текущий стабильный `publicSubscriptionToken` STEALTHNET.

Создание новых composite subscriptions отключается до начала cutover. Миграция является возобновляемой и хранит состояние по каждому клиенту.

### 8.2 Пересоздание

Для каждой действующей подписки создается один новый обычный Remnawave user:

```text
createdAt             = исходная дата создания действующей подписки
expireAt              = точная текущая дата окончания
activeInternalSquads  = squad текущего тарифа
status                = текущий допустимый статус
trafficLimitBytes     = 0 при LOCAL_SQUAD
trafficLimitStrategy  = NO_RESET при LOCAL_SQUAD
```

Remnawave 2.8 поддерживает передачу `createdAt`, `expireAt` и UUID при создании. Новый пользователь создается до удаления старых component users. После `GET`-проверки и проверки получения обычной subscription STEALTHNET атомарно переключает `Subscription.remnawaveUuid`.

Стабильный `publicSubscriptionToken` STEALTHNET не меняется. Старые component users остаются на короткий grace-период, затем revoke/delete выполняется только после подтверждения нового доступа.

Старые whitelist limits и использованный трафик не сохраняются:

- Remnawave traffic limit нового пользователя — `0` для локального режима;
- локальный `usedBytes` — `0`;
- новый baseline снимается в момент cutover;
- старые component quota и checkpoints удаляются после проверки.

### 8.3 Rollout

1. Backup STEALTHNET и Remnawave PostgreSQL.
2. Dry-run inventory без изменений.
3. Миграция внутреннего тестового клиента.
4. Проверка обычной subscription, Default, Whitelist, EU-exclusion, expireAt и revoke.
5. Пакетная миграция оставшихся текущих клиентов с журналом результата.
6. Observe-only учет без отзыва squad.
7. Включение enforcement после сверки трафика.
8. Удаление composite-кода и данных только после завершенной сверки.

## 9. Этапы реализации

Будут выпущены четыре взаимосвязанных плана-ТЗ:

1. **Подготовка удаления composite-sub и возврат runtime к одной подписке.** Инвентаризация, классификация полезных изменений, запрет создания новых components, перевод рабочих путей на одного обычного Remnawave user и сохранение только временного migration reader для старых данных.
2. **Модель тарифов, Trial, периодов и полная админ-интеграция.** Взаимоисключающие режимы лимита, локальные периоды, дополнительные гигабайты и UI/API.
3. **API-брокер, учет, уведомления и enforcement.** Автоматическое разрешение нод squad, bounded checkpoint, пакетная статистика, пороги и отзыв только учитываемого squad.
4. **Конвертация, миграция клиентов и production cutover.** Формула переходов, пересоздание обычных Remnawave users, обнуление whitelist history, observe-only rollout, затем физическое удаление оставшихся composite tables/code и приемочные проверки.

Каждый этап завершается работающим и отдельно проверяемым состоянием. Composite runtime отключается на первом этапе, но migration reader и старые данные сохраняются до четвертого этапа. Физическое удаление происходит только после успешного пересоздания и проверки обычных подписок.

## 10. Критерии приемки

- У каждого клиента одна STEALTHNET subscription, один Remnawave user и одна обычная subscription.
- Тариф `Default + Whitelist` списывает только трафик нод `Whitelist`; EU/Default не влияет на локальный счетчик.
- Администратор выбирает только назначенные squad и один учитываемый squad; ручной настройки pool/hosts/nodes нет.
- Локальная таблица checkpoint ограничена одной строкой на подписку.
- Пороги `50/25/10/3/0` отправляются один раз за период.
- Исчерпание удаляет только `Whitelist`, а Default продолжает работать.
- Персональный reset следует дате покупки, а не первому числу месяца.
- Trial имеет отдельный лимит.
- Продление и конвертация вверх/вниз сохраняют действующую формулу дней.
- `CURRENT_PERIOD` и `WHILE_TARIFF_ACTIVE` работают по согласованному жизненному циклу и подходят для будущей покупки гигабайт.
- Текущие клиенты мигрированы на новых обычных Remnawave users с правильными `createdAt` и `expireAt`; старый whitelist usage начинается с нуля.
- При ошибке источника статистики система не отбирает доступ и не начисляет неподтвержденные данные.

## 11. Осознанно не включено

- Отдельный микросервис/очередь для 10–1000 клиентов.
- История каждого пятиминутного sample.
- Ручная настройка балансировщика в STEALTHNET.
- Изменения или fork Remnawave/Xray.
- Пользовательская покупка гигабайт в первой реализации; модель начислений и API подготавливаются сразу, платежный продукт добавляется отдельным небольшим этапом.
