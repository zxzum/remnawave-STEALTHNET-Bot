# Дизайн фикса пробного периода после покупки

## Цель

Исправить поведение пробного периода в продукте **Лазейка ВПН**:

1. Любая оплаченная VPN-подписка навсегда сжигает право на пробный период.
2. Это правило действует и для клиентов, которые покупали подписку раньше.
3. У клиента не остаётся одновременно платная подписка и отдельная trial-подписка, включая истёкший trial.
4. В новом кабинете истёкший trial показывает понятное сообщение и ведёт к тарифам.

Технические имена, существующие пути, Prisma-модель и legacy-идентификаторы `stealthnet` не переименовываются.

## Инварианты

- `Client.trialUsed` — монотонный флаг: после платной VPN-покупки он становится `true` и этим изменением не сбрасывается.
- Платной покупкой считается успешная покупка VPN-подписки, включая обычный тариф и другие существующие потоки, которые создают/активируют собственную платную `Subscription`.
- Пополнение баланса, proxy/sing-box услуги и отдельные доп.опции не сжигают trial сами по себе.
- Подарочная покупка не считается платной собственной подпиской получателя. Существующая семантика плательщика и подарка сохраняется.
- Trial-only клиент может активировать trial по текущим правилам.
- Клиент с `trialUsed=true` не может активировать ни legacy trial, ни trial из таблицы `Trial`.
- Удаление trial не должно быть выполнено только удалением строки из PostgreSQL: Remnawave-пользователь удаляется существующим lifecycle с retry.

## Backend: рабочий поток покупки

Правило ставится в общем потоке обработки оплаченного VPN-платежа, чтобы его применяли webhook-и, оплата с баланса, админские действия и автопродление, использующие существующий activation service.

Порядок:

1. Платёж атомарно переходит в `PAID`.
2. Для VPN-покупки выполняется идемпотентный update конкретного клиента: `trialUsed=false → true`.
3. После этого обрабатывается активация/продление подписки.
4. Если у клиента есть отдельные trial-подписки, они помечаются на удаление через существующий `deleteSingleSubscription` последовательно. Платёж не откатывается из-за временной ошибки Remnawave.
5. Ошибка удаления оставляет запись в текущей очереди `deletionRequestedAt/syncStatus/syncRequiredAt`; существующий maintenance retry повторяет операцию.

Флаг выставляется до удаления trial и не откатывается. Поэтому даже при недоступном Remnawave повторная попытка получить trial невозможна.

При конвертации самого trial в тариф текущая подписка сохраняет UUID/ссылку; после конвертации она больше не является trial. Остальные trial-подписки клиента удаляются по тому же правилу.

Покупка без trial не вызывает внешних запросов на удаление: сначала выполняется дешёвая выборка trial-подписок клиента, и при пустом результате flow заканчивается.

## Backend: доступность trial

Оба существующих клиентских потока учитывают один и тот же флаг:

- `POST /client/trial` проверяет `trialUsed` до legacy-активации и сохраняет текущую атомарную защиту от параллельной активации.
- `GET /client/trials/available` возвращает пустой список для `trialUsed=true`, чтобы кабинет не показывал кнопку.
- `POST /client/trials/:id/activate` повторно проверяет `trialUsed` непосредственно перед созданием trial-подписки. Проверка не полагается только на состояние фронтенда.

Проверки выполняются по клиенту и индексируемым связям; нового глобального запроса по всей базе на каждый вход в кабинет нет.

## Разовая очистка существующих данных

Добавляется отдельная идемпотентная operational-команда, по умолчанию работающая в dry-run режиме. Постоянный cron и полный периодический скан не добавляются.

### Dry-run

Команда только читает базу и показывает:

- сколько клиентов получат `trialUsed=true` по истории успешных VPN-покупок;
- сколько trial-подписок конфликтуют с собственной платной подпиской или исторической покупкой;
- список/счётчик кандидатов, ограниченный размером батча.

В dry-run нет запросов к Remnawave и нет записей в базу.

### Apply

После явного `--apply` команда:

1. батчами выставляет `trialUsed=true` клиентам с историей успешной VPN-покупки;
2. выбирает конфликтующие trial-подписки небольшими батчами;
3. перед каждым удалением повторно сохраняет `trialUsed=true` для владельца;
4. последовательно вызывает `deleteSingleSubscription`;
5. продолжает обработку остальных кандидатов при единичной ошибке и оставляет неудачные удаления текущему retry-механизму;
6. выводит итог: отмеченные клиенты, удалённые trial, отложенные/неудачные удаления.

Команда не использует `DELETE`/`UPDATE` напрямую для trial-строк и не удаляет Remnawave-пользователей параллельно. Повторный запуск безопасен: уже установленный флаг не меняется, уже удалённые trial не находятся, pending deletion обрабатывается штатным retry.

## Новый кабинет

Изменяется только `frontend/src/cabinet/pages/Cabinet.tsx`, соответствующий приложенному экрану. Classic/Stealth-страницы не затрагиваются.

В `MainSubscriptionCard` для `sub.isTrial === true && sub.status === "expired"`:

- вместо трафика, даты и устройств показывается центрированный блок;
- текст: `Пробный период закончился`;
- рядом/ниже — кнопка `Все тарифы`, ведущая на `/cabinet/tariffs`;
- статус карточки отображается как завершённый, а не как `Активна`.

Активный trial и платные подписки сохраняют текущую разметку и поведение.

## Проверки

До production-кода добавляются минимальные регрессии:

- оплаченный VPN-тариф устанавливает `trialUsed=true`;
- top-up и отдельная доп.опция не устанавливают этот флаг;
- повторная обработка одного платежа остаётся идемпотентной;
- `trialUsed=true` блокирует оба trial endpoint-а;
- разовая очистка в dry-run не пишет в БД и не вызывает Remnawave;
- cleanup использует существующий lifecycle и оставляет ошибку для retry;
- истёкший trial в новом кабинете получает специальное состояние, остальные карточки не меняются;
- backend test suite и frontend build проходят.

## Ограничения и отказоустойчивость

- Нет нового постоянного полного сканирования базы.
- В штатной покупке выполняется только адресная работа с текущим клиентом.
- Внешние удаления выполняются последовательно и небольшими батчами.
- Оплата и `trialUsed=true` не зависят от успешности последующего удаления в Remnawave.
- При временной ошибке внешнего сервиса данные не теряются и повторяются существующим maintenance.
- Новая миграция схемы не нужна: используется существующий `trialUsed`, `trialId` и lifecycle удаления.

## Не входит в задачу

- Изменение Classic/Stealth-кабинетов.
- Переписывание платёжных провайдеров.
- Новый scheduler или постоянная фоновая синхронизация.
- Удаление подарочных подписок, не являющихся trial-подписками владельца.
- Переименование legacy-технических идентификаторов.
