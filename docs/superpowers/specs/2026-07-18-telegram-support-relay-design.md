# Telegram Support Relay — дизайн

**Дата:** 2026-07-18  
**Статус:** согласованная архитектура, ожидает финального просмотра перед implementation-планом

## 1. Цель

Добавить в существующего Telegram-бота прямую переписку клиента с менеджерами через закрытую Telegram-супергруппу с включёнными темами (forum topics).

Это не тикет-система:

- клиент пишет обычные сообщения боту;
- менеджер отвечает в Telegram-теме клиента;
- бот копирует ответ обратно в личный чат клиента;
- нет номера обращения, формы создания, приоритета, SLA и отдельного интерфейса переписки в панели.

Система должна оставаться удобной при 1000 и более диалогах, ожидающих ответа, не блокировать остальные функции бота и не дублировать историю сообщений в базе данных.

## 2. Выбранный подход

Для каждого клиента создаётся одна постоянная тема в закрытой группе поддержки.

- `🟠` в начале названия означает, что последнее успешно доставленное сообщение пришло от клиента и нужен ответ менеджера.
- `🟢` означает, что последнее успешно доставленное сообщение отправил менеджер.
- Новое сообщение клиента повторно использует существующую тему, поднимает её в списке и переводит в `🟠`.
- Успешный ответ менеджера переводит тему в `🟢`.
- Отвеченные неактивные темы автоматически закрываются. Новое сообщение клиента открывает ту же тему повторно.
- Неотвеченные темы автоматически не закрываются.

Отклонённые варианты:

1. **Тема на каждое обращение:** создаёт дубли и быстро засоряет группу.
2. **Все клиенты в одной теме:** ответы легко отправить не тому клиенту, очередь не читается.
3. **Внешний helpdesk:** дублирует существующие данные клиентов и добавляет лишнюю инфраструктуру до появления реальной многоканальности или SLA.

## 3. Пользовательский сценарий

1. Клиент открывает существующий раздел `/support` или кнопку «Помощь».
2. Нажимает «Написать в поддержку».
3. Бот включает режим прямой переписки и показывает короткое сообщение: всё отправленное далее будет передано менеджеру.
4. Клиент отправляет текст, фото, видео, документ, аудио, голосовое сообщение, анимацию или стикер.
5. Бот через `copyMessage` копирует сообщение в тему клиента без метки пересылки.
6. Менеджер отвечает обычным сообщением в этой теме.
7. Бот через `copyMessage` доставляет ответ в личный чат клиента.
8. Клиент нажимает «Завершить диалог» или возвращается в главное меню, чтобы последующие сообщения снова обрабатывались обычными сценариями бота.

Команды бота и нажатия меню всегда имеют приоритет над relay-режимом. Ответ менеджера доставляется клиенту независимо от того, включён ли у клиента режим ввода поддержки в данный момент.

## 4. Архитектура

### 4.1. Telegram-бот

Новый модуль relay отвечает только за:

- распознавание клиентского и менеджерского направления;
- получение или создание темы;
- `copyMessage` между личным чатом и группой;
- изменение индикатора темы только при смене состояния;
- команды менеджеров `/unanswered` и `/client`;
- понятное сообщение об ошибке доставки.

Существующий бот продолжает использовать один токен и один процесс. Отдельный бот поддержки и отдельный сервис не создаются.

### 4.2. Backend

Backend остаётся единственным владельцем PostgreSQL/Prisma и предоставляет bot-only API под уже используемой проверкой `X-Telegram-Bot-Token`.

Минимальные операции API:

- найти клиента по Telegram ID и получить/создать связь с темой;
- атомарно зарегистрировать созданный `message_thread_id`;
- включить или выключить клиентский relay-режим;
- отметить успешно доставленное сообщение клиента;
- отметить успешно доставленный ответ менеджера;
- вернуть очередь ожидающих ответа с cursor-пагинацией;
- вернуть компактный контекст клиента для темы;
- вернуть отвеченные неактивные темы для фонового закрытия.

Публичных endpoint'ов не добавляется. Запросы из закрытой группы дополнительно принимаются только для настроенного `support_group_id`.

### 4.3. База данных

Добавляется одна модель `SupportConversation` без таблицы сообщений:

| Поле | Назначение |
|---|---|
| `id` | внутренний идентификатор |
| `clientId` | уникальная связь с существующим `Client` |
| `topicId` | уникальный Telegram `message_thread_id`, nullable до создания темы |
| `relayEnabled` | принимает ли бот произвольные сообщения клиента как сообщения поддержки |
| `waitingForSupport` | нужен ли ответ менеджера |
| `lastClientMessageAt` | время последней успешной доставки в группу |
| `lastSupportMessageAt` | время последней успешной доставки клиенту |
| `topicClosedAt` | закрыта ли неактивная тема ботом |
| `createdAt`, `updatedAt` | служебные даты |

Индексы:

- unique по `clientId`;
- unique по `topicId`;
- составной индекс `(waitingForSupport, lastClientMessageAt)` для очереди;
- индекс `(waitingForSupport, lastSupportMessageAt)` для очистки отвеченных тем.

Тексты и файлы в базе повторно не сохраняются: история уже находится в личном чате клиента и закрытой группе. Существующие `Ticket` и `TicketMessage` не используются.

## 5. Работа с 1000 неотвеченных диалогов

### 5.1. Очередь

Команда `/unanswered` доступна только в настроенной группе поддержки и показывает:

- общее количество ожидающих ответа;
- первые 20 диалогов, начиная с самого старого;
- время ожидания;
- ссылку непосредственно на тему;
- кнопки следующей/предыдущей страницы.

Запрос использует cursor-пагинацию по `(lastClientMessageAt, id)`, а не медленный `OFFSET` на больших объёмах.

### 5.2. Жизненный цикл тем

- Неотвеченная тема остаётся открытой независимо от возраста.
- Отвеченная тема закрывается после настраиваемого периода без активности; начальное значение — 7 дней.
- Новое сообщение открывает старую тему вместо создания новой.
- Удалённая вручную тема обнаруживается по ошибке Telegram API; связь очищается и тема создаётся заново один раз.

Фоновая очистка обрабатывает небольшие страницы записей, поэтому не создаёт всплесков запросов к Telegram.

## 6. Данные клиента и связь с панелью

Контекст клиента менеджеру нужен, но отдельный экран переписки в панели не нужен.

При первом создании темы бот публикует компактную карточку:

- имя/Telegram username и Telegram ID;
- email, если он есть;
- баланс и валюта;
- состояние блокировки;
- активная подписка: тариф, дата окончания и состояние;
- дата регистрации;
- внутренний client ID.

Карточка содержит кнопку «Открыть клиента в панели». Существующая страница клиентов получает поддержку deep link вида `/admin/clients?clientId=<id>` и после обычной админской авторизации открывает уже существующую подробную карточку клиента.

Команда `/client` внутри темы повторно загружает актуальный компактный контекст. Данные не запрашиваются на каждое сообщение и не кэшируются надолго, поэтому relay остаётся быстрым, а менеджер получает свежие сведения по запросу.

В Telegram не выводятся пароли, токены, URL подписок, платёжные реквизиты и другие секреты.

## 7. Производительность

### 7.1. Параллельность

Текущий последовательный long polling не должен заставлять медленное сообщение одного клиента задерживать остальных. Используется официальный runner для grammY с ограниченной параллельностью.

Порядок сохраняется ключом выполнения:

- личный чат: Telegram chat ID клиента;
- группа поддержки: сочетание group ID и `message_thread_id`.

Разные клиенты и разные темы обрабатываются параллельно, сообщения одного диалога — строго последовательно.

### 7.2. Telegram API

- Для передачи всех поддерживаемых типов используется один вызов `copyMessage`, без скачивания и повторной загрузки файлов.
- Переименование темы выполняется только при реальной смене `🟠/🟢`.
- Ошибки ограничения частоты и временные ошибки Telegram повторяются с учётом `retry_after`; собственный самописный scheduler не создаётся.
- Параллельность ограничена, чтобы не усугублять rate limit при всплеске сообщений.

### 7.3. Backend и кэш

- В горячем пути — индексированный поиск/обновление одной `SupportConversation`.
- Бот держит ограниченный in-memory cache соответствий `telegramId/clientId/topicId`; база остаётся источником истины после рестарта.
- Кэш не хранит профиль, баланс или подписку.
- Создание темы защищено unique-ограничениями и последовательной обработкой одного клиента, поэтому два одновременных сообщения не создают две темы.
- Долгие запросы профиля не входят в путь доставки каждого сообщения.

Целевые проверки на тестовом окружении:

- запрос страницы из 20 неотвеченных среди 10 000 связей использует индекс и выполняется без полного сканирования;
- обычная маршрутизация добавляет один короткий backend round trip плюс Telegram `copyMessage`;
- медленная доставка одному клиенту не блокирует сообщения других клиентов;
- потребление памяти кэшем ограничено фиксированным размером.

## 8. Надёжность и ошибки

- Состояние меняется на `waitingForSupport=true` только после успешного копирования сообщения в группу.
- Состояние меняется на `waitingForSupport=false` только после успешной доставки ответа клиенту.
- Если клиент заблокировал бота, в теме появляется служебное предупреждение, а диалог остаётся неотвеченным.
- Если группа или права бота настроены неверно, клиент получает нейтральное сообщение о временной недоступности; сообщение не помечается доставленным.
- Если backend временно недоступен, выполняется короткий ограниченный retry. Бесконечной очереди в памяти нет.
- Сервисные сообщения, сообщения самого бота и сообщения вне настроенной группы не пересылаются.
- Альбомы Telegram сохраняют порядок; допустима доставка элементов отдельными `copyMessage`, без собственного медиахранилища.
- При старте бот проверяет существование группы, режим forum и необходимые права: чтение сообщений, публикация, создание/редактирование/закрытие тем.

## 9. Безопасность и защита от злоупотреблений

- Relay работает только с точным `support_group_id`, заданным в настройках.
- Группа закрытая; бот является администратором, privacy mode настроен так, чтобы бот видел ответы менеджеров.
- Любой участник этой закрытой группы считается менеджером поддержки. Управление доступом выполняется через членство в группе.
- Клиент может писать только в собственную тему: назначение определяется серверной связью с Telegram ID, а не входными данными клиента.
- Используются существующие ограничения бота на частоту сообщений; для relay добавляется отдельный короткий burst-limit на клиента.
- Неподдерживаемые типы сообщений получают понятный ответ и не ломают режим поддержки.
- Callback data и параметры API валидируются; bot token сравнивается существующим защищённым механизмом.

## 10. Настройки

В существующую панель настроек добавляются только необходимые параметры:

- включить прямую поддержку;
- Telegram ID закрытой forum-группы;
- срок автозакрытия отвеченных тем, по умолчанию 7 дней;
- текст приветствия режима поддержки.

Существующий `supportLink` может продолжить обслуживать внешнюю ссылку, но новая кнопка прямой переписки использует relay. `ticketsEnabled` не связан с relay и может быть выключен.

## 11. Проверки

Минимальный автоматизированный набор:

1. Миграция и backend: одна связь на клиента, одна связь на тему, сортировка очереди от старых к новым.
2. Состояние: клиентское сообщение даёт `🟠`; неудачная доставка не меняет состояние; успешный ответ даёт `🟢`.
3. Маршрутизация: разные типы сообщений вызывают `copyMessage` в правильном направлении.
4. Изоляция: сообщение из другой группы и сообщение без известной темы не доставляются клиенту.
5. Порядок: сообщения одного клиента обрабатываются последовательно, двух разных клиентов — независимо.
6. Deep link панели открывает карточку указанного клиента после авторизации.
7. `/unanswered` использует cursor-пагинацию и не теряет записи с одинаковым временем.

Ручная smoke-проверка в тестовой закрытой forum-группе:

- первый вход, создание темы и карточки;
- двусторонние текст и каждый поддерживаемый media type;
- несколько быстрых сообщений подряд;
- блокировка бота клиентом;
- закрытие, повторное открытие и ручное удаление темы;
- перезапуск bot/backend между сообщениями;
- очередь более чем из одной страницы.

## 12. Развёртывание

1. Применить Prisma-миграцию и backend API без включения функции.
2. Добавить настройки и deep link панели.
3. Добавить relay в бота и автоматические проверки.
4. Создать закрытую супергруппу, включить темы, выдать боту необходимые права.
5. Записать group ID в панели и выполнить startup-проверку.
6. Включить relay сначала для внутреннего тестового аккаунта, затем для всех клиентов.
7. Наблюдать ошибки Telegram, задержку доставки и размер очереди.

Откат выполняется выключением relay в панели. Существующее меню, продажи и клиентская база продолжают работать; созданные темы и одна таблица связей не мешают остальному проекту.

## 13. Не входит в первую версию

- назначение диалога конкретному менеджеру;
- SLA, приоритеты, теги и категории;
- отдельная копия переписки в админ-панели;
- полнотекстовый поиск по сообщениям;
- AI-ответы и автоответы;
- омниканальность;
- собственное файловое хранилище;
- аналитика эффективности менеджеров.

Добавлять это следует только при подтверждённой операционной необходимости. Первая версия решает одну задачу: быстрая и контролируемая прямая переписка в Telegram при большой очереди ожидающих ответа.
