# Лазейка ВПН — пошаговая регистрация по email

## Цель

Исправить регистрацию в кабинете так, чтобы при включённом подтверждении email письмо отправлялось сразу после ввода почты, а реальный аккаунт создавался только после перехода по ссылке и установки пароля.

## Поведение

### Подтверждение email включено

1. Пользователь вводит email и нажимает продолжить.
2. Backend создаёт pending-заявку без пароля и отправляет письмо подтверждения.
3. UI показывает alert с адресом, на который отправлено письмо, и действие повторной отправки.
4. Повторная отправка защищена от флуда:
   - cooldown 60 секунд для одного нормализованного email;
   - не более 5 отправок за 1 час с одного IP;
   - лимит проверяется на backend и действует для первой и повторных отправок.
5. Переход по ссылке только отмечает pending-заявку как подтверждённую и возвращает временный registration token. `Client` ещё не создаётся и авторизация не выдаётся.
6. Пользователь попадает на шаг установки пароля.
7. После успешной установки пароля backend создаёт `Client`, удаляет pending-заявку, выдаёт клиентскую сессию и запускает существующую обработку нового клиента.
8. Если пароль не задан, аккаунта нет. Пользователь может снова открыть регистрацию, указать тот же email и запросить новую ссылку; после успешной отправки старые ссылки становятся недействительными.
9. Просроченная или отозванная ссылка не создаёт аккаунт и предлагает зарегистрироваться заново.

### Подтверждение email отключено (`skipEmailVerification`)

1. После ввода email пользователь сразу переходит к шагу установки пароля.
2. Письмо не отправляется.
3. После установки пароля используется существующая регистрация без email-подтверждения.
4. После завершения сохраняется тот же необязательный шаг 2FA, если он включён.

## Backend-дизайн

Используется существующая модель `PendingEmailRegistration`; отдельная сущность для регистрации не добавляется.

Изменения модели:

- `passwordHash` становится nullable и заполняется только после подтверждения email и установки пароля;
- `emailVerifiedAt` хранит факт перехода по ссылке;
- `registrationIp` хранит IP для лимита отправок;
- `revokedAt` инвалидирует старые pending-заявки;
- индексы по `email + createdAt` и `registrationIp + createdAt` поддерживают проверки cooldown/лимита.

API-поток:

- `POST /client/auth/register` принимает email без пароля только в режиме подтверждения, выполняет rate limit, создаёт pending-заявку и отправляет письмо;
- `POST /client/auth/verify-email` проверяет ссылку, отмечает `emailVerifiedAt` и возвращает `{ registrationToken, email }`;
- `POST /client/auth/complete-registration` принимает registration token и новый пароль, атомарно создаёт Client и удаляет pending-заявку;
- режим `skipEmailVerification` сохраняет текущую регистрацию по email+паролю.

При ошибке отправки новая pending-заявка удаляется, а предыдущая действующая ссылка остаётся рабочей. Старые заявки отзываются только после успешной отправки новой ссылки.

## Frontend-дизайн

Основной flow остаётся в `frontend/src/cabinet/pages/Auth.tsx`:

- убрать промежуточный экран «Аккаунт успешно создан» до подтверждения email;
- передавать email на backend сразу после email-шага, если подтверждение включено;
- принимать registration token из verify-страницы и открывать шаг пароля;
- после завершения регистрации показывать существующий необязательный 2FA-шаг, если он включён;
- после завершения onboarding открыть modal «Аккаунт успешно создан» с рекомендацией привязать Telegram в настройках профиля.

`VerifyEmail` больше не авторизует пользователя и перенаправляет на регистрацию со временным registration token. При повторной отправке UI использует тот же endpoint регистрации, а ответ с rate limit показывает пользователю время до следующей попытки.

## Проверки

Минимальный тестовый набор:

- email-only запрос в режиме подтверждения создаёт pending-заявку без `Client` и без `passwordHash`;
- повторная отправка раньше cooldown возвращает 429;
- превышение IP-лимита возвращает 429;
- переход по ссылке только помечает pending-заявку подтверждённой;
- complete-registration без подтверждения, с просроченным или отозванным token не создаёт `Client`;
- complete-registration с валидным token создаёт ровно один `Client` и удаляет pending-заявку;
- режим `skipEmailVerification` ведёт сразу к шагу пароля;
- frontend показывает alert после отправки письма и success modal после создания аккаунта.
