# ТЗ: доработка страницы «Клиенты» админ-панели

## 1. Цель

Переработать страницу `/admin/clients` и карточку клиента так, чтобы администратор быстро видел фактическое состояние подписок и подключений, мог управлять подписками из одного места, а тяжёлые данные загружались только по запросу.

Работа выполняется в отдельном наборе изменений от переработки функционала бота, ответов и баннеров.

## 2. Что уже есть в текущей реализации

- список клиентов с серверным поиском и пагинацией;
- фильтры «все / активные / заблокированные» и «все / есть подписка / активная подписка»;
- несколько подписок клиента, включая подаренные;
- вкладки профиля, подписок, устройств, действий и услуг;
- данные Remnawave по трафику, устройствам и последнему времени подключения;
- endpoint аудита клиента и статистики использования трафика.

Ограничения текущей реализации, которые покрывает это ТЗ:

- UI всегда запрашивает 20 клиентов, хотя backend допускает до 100;
- поиск применяется после Enter/кнопки;
- статус клиента может показывать squad вместо ноды;
- модалка загружает несколько тяжёлых источников сразу при открытии;
- изменения подписки не имеют единого источника состояния для всех вкладок;
- статистика трафика привязана к основной подписке;
- API текущих сессий и журнала посещённых ресурсов в админском контуре не определён.

## 3. Страница списка клиентов

### 3.1. Колонка подключения

Вместо squad показывать ноду Remnawave, к которой клиент подключался последней.

Правила:

1. Источник истины — `userTraffic.lastConnectedNodeUuid` для каждой подписки.
2. UUID ноды преобразуется в отображаемое имя через справочник нод Remnawave.
3. При нескольких подписках показывать ноду с самым свежим временем подключения и время этого подключения.
4. Если нода не найдена — показывать `Нода <короткий UUID>` и не подменять её squad.
5. Если подключений не было — показывать «Нет подключений».
6. Online/offline оставить отдельным признаком; «последняя нода» не означает, что клиент сейчас онлайн.

Backend должен вернуть в DTO списка нормализованные поля `lastConnectedNode` и `lastConnectedAt`; frontend не должен угадывать ноду по `activeInternalSquads`.

### 3.2. Поиск

- Поиск выполняется с debounce 300–500 мс после начала ввода.
- При изменении строки страница сбрасывается на 1.
- Пустая строка возвращает полный список.
- Старый запрос не должен перезаписывать результат более нового запроса.
- Кнопку «Найти» и обязательный Enter убрать; допустима кнопка очистки.
- Поиск должен работать по username, email, Telegram ID, внутреннему ID, referral code и UUID подписки.

### 3.3. Фильтры

Сохранить фильтр блокировки и добавить единый блок фильтров подписок:

- наличие подписки: нет / любая / активная;
- конкретный тариф — multi-select с поиском;
- тип: trial / обычная / подарочная / полученная в подарок;
- статус подписки: активна / истекла / отключена / ожидает удаления;
- нода последнего подключения;
- наличие текущей сессии.

Фильтры передаются на backend и применяются в запросе к БД. Фильтрация только загруженных 20/100 строк не допускается.

### 3.4. Пагинация

- В селекторе размера страницы: 20, 50, 100.
- Значение сохраняется в URL query-параметре и восстанавливается после обновления страницы.
- При смене размера страницы страница сбрасывается на 1.
- Backend ограничивает значение максимумом 100.
- На странице отображать диапазон элементов и общее количество.

### 3.5. Squads

Squad не удалять из управления подпиской, но не использовать как статус подключения.

- В списке подписок показывать все squads с понятными названиями и типом (internal/метка).
- `WHITELIST` отображать как обычную squad с отдельным бейджем, без попытки скрыть или заменить её.
- В карточке подписки явно разделить «Squads подписки» и «Последняя нода подключения».

## 4. Новая модалка клиента

### 4.1. Общая структура

Модалка должна быть компактной и состоять из:

1. шапки с клиентом, блокировкой, online-статусом и быстрыми действиями;
2. краткой сводки;
3. вкладок: «Профиль», «Подписки», «Трафик», «Активность», «Устройства», «Действия»;
4. фиксированной нижней панели с «Сохранить», «Отмена» и индикатором несохранённых изменений.

Вкладки «Трафик» и «Активность» загружают данные только при первом переходе на них. Повторный запрос выполняется по явному «Обновить» или после действия, меняющего соответствующие данные.

### 4.2. Мобильная адаптация

- На ширине до 640 px модалка занимает весь экран, без горизонтального скролла.
- Шапка и нижняя панель остаются доступными при вертикальной прокрутке.
- Вкладки прокручиваются горизонтально и не переносят контент в несколько трудночитаемых строк.
- Сводка переходит в одну колонку.
- Таблицы подписок, сессий и журнала превращаются в карточки.
- Все интерактивные элементы имеют область нажатия не менее 44 px.
- Длинные UUID, URL и user-agent обрезаются с копированием по нажатию.

### 4.3. Единое состояние

Ввести единый объект состояния клиента на уровне модалки:

- client;
- subscriptions;
- remnawave data per subscription;
- traffic;
- devices;
- activity;
- sessions.

После любого успешного изменения подписки:

- обновляется единый store/modal state;
- перерисовываются шапка, сводка, список подписок, лимиты, срок, тариф, squads и счётчики вкладок;
- выполняется один согласованный refetch нужных ресурсов, без каскада независимых запросов;
- при ошибке изменения локальное состояние не считается сохранённым и показывается причина.

Закрытие модалки с изменениями должно либо сохранять их, либо явно предупреждать администратора.

## 5. Вкладка «Подписки» и управление

Для каждой подписки показывать:

- индекс и тип: trial/обычная/подарочная/полученная в подарок;
- тариф, цену и срок действия;
- статус Remnawave;
- лимит трафика и использованный трафик;
- лимит устройств и число устройств;
- auto-renew;
- squads;
- последнюю ноду и время подключения;
- ссылку подписки с копированием.

Действия доступны согласно правам администратора и требуют подтверждения для потенциально разрушающих операций:

- изменить тариф;
- продлить или изменить дату окончания;
- изменить лимит трафика и устройств;
- включить/выключить автопродление;
- сбросить трафик;
- revoke/перевыпустить ссылку;
- отключить/включить подписку;
- удалить/отозвать подписку.

### 5.1. Конвертация trial

Добавить действие «Перевести trial в обычную подписку»:

- доступно только для trial;
- администратор выбирает тариф и ценовую опцию/длительность;
- отображается предпросмотр: старый тип, новый тариф, срок, лимиты и итоговая цена;
- операция выполняется атомарно на backend;
- повторный клик не создаёт вторую подписку или повторное списание;
- после успеха обновляются все вкладки и список клиентов;
- операция записывается в аудит с администратором, исходной и новой подпиской.

## 6. Вкладка «Трафик» — монитор подключений

Вкладка работает только при открытии.

### 6.1. Активные сессии

Показывать:

- состояние: активна/завершена;
- время начала и последнюю активность;
- текущую ноду и её UUID;
- протокол/тип подключения, если доступен;
- IP и user-agent — только администраторам с соответствующим правом;
- входящий/исходящий трафик.

Добавить ручное обновление и polling только пока вкладка открыта. При закрытии вкладки polling прекращается.

Backend-контракт: `GET /admin/clients/:id/sessions?active=true|false`, пагинация и фильтр по подписке. Источник данных — Remnawave/агент; UI не должен имитировать сессии по одному `onlineAt`.

### 6.2. Журнал запросов и посещённых ресурсов

Если логирование включено и данные доступны, показывать журнал:

- timestamp;
- нода;
- ресурс/домен или URL согласно реально собираемому формату;
- метод;
- код ответа;
- длительность;
- объём ответа;
- связанную сессию.

Поддержать диапазон дат, поиск по ресурсу, фильтр по ноде и пагинацию. Если логирование выключено или записей нет, показывать понятное состояние «Журнал не ведётся», а не пустую ошибку.

Не сохранять и не показывать содержимое запросов, токены, пароли и query-параметры с секретами. Хранение, TTL и доступ к журналу должны быть ограничены политикой приватности и ролью администратора.

## 7. Вкладка «Активность»

Показывать временную шкалу действий клиента и администраторов:

- входы и подключения;
- создание, изменение, продление, конвертация и отзыв подписки;
- изменения тарифа, лимитов, squads и устройств;
- платежи, возвраты и подарки;
- блокировка/разблокировка;
- отправленные системные действия, если они логируются.

Для каждой записи: дата, тип события, инициатор, краткое описание, результат и ссылка на связанную сущность. Добавить фильтр по типу события и периоду. Вкладка загружается лениво с cursor pagination.

## 8. Backend и безопасность

- Все новые endpoints защищены текущей admin-auth и проверкой section/action permissions.
- Данные по нескольким подпискам агрегируются на backend; frontend не делает N запросов на каждую строку таблицы.
- Для списка клиентов использовать batch-запросы к Remnawave или кэш справочника нод.
- Ошибка получения данных одной подписки не должна скрывать остальные данные клиента; в ответе нужна частичная ошибка с понятным статусом.
- Все мутирующие действия идемпотентны либо защищены idempotency key.
- Изменения и чувствительные просмотры пишутся в admin audit.
- Секретные поля Remnawave не возвращаются в DTO списка и не отображаются в модалке без отдельного явного действия.

## 9. Критерии приёмки

1. В списке клиентов отображается последняя нода, а не squad; при отсутствии ноды показывается корректный fallback.
2. Поиск обновляет результаты во время ввода и не допускает гонок старых запросов.
3. Можно выбрать 20/50/100 строк, состояние сохраняется в URL.
4. Фильтр по конкретному тарифу и типу подписки работает по всему набору клиентов.
5. WHITELIST и другие squads отображаются без потери данных и не используются как нода.
6. Модалка пригодна для телефона 360 px: без горизонтального скролла и с доступными основными действиями.
7. Изменение подписки сразу отражается во всех связанных блоках без закрытия модалки.
8. Трафик, сессии и активность не запрашиваются до открытия соответствующей вкладки.
9. При отсутствии логирования журнал объясняет причину.
10. Trial можно конвертировать в обычную подписку с подтверждением, аудитом и обновлением UI.
11. Нет утечки секретов и доступа к данным за пределами прав администратора.
12. Добавлены backend contract/integration tests для ноды, фильтров, конвертации и permission checks, а также responsive smoke-check для модалки.

## 10. Границы работ и порядок внедрения

### Этап 1 — список клиентов

DTO последней ноды, batch-справочник нод, live search, фильтры и размер страницы.

### Этап 2 — состояние и модалка

Единое состояние, мобильная раскладка, вкладки и синхронизация после мутаций.

### Этап 3 — управление подписками

Конвертация trial, действия по подписке, permissions и аудит.

### Этап 4 — мониторинг

Сессии, журнал запросов и ленивые загрузки. Если источник логов не существует, сначала реализовать его контракт, хранение и политику TTL; frontend без источника данных не считать готовым.

Изменения этапов 1–4 коммитить отдельно, чтобы их можно было безопасно объединить с веткой агента, меняющего бота, ответы и баннеры.
